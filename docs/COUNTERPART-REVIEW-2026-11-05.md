# 本草 v8 对家评审：功能完成之后，用户为什么仍可能不满意

> 评审日期：2026-11-05  
> 评审对象：POPO 线上版本 8 及本地源代码  
> 评审链接：[本草 · 中医健康助手](https://bencao-tcm-tm.popo.baidu-int.com/)  
> 评审方式：代码走查、验收记录复核、线上页面走查、已有 27 项 Node 测试复核

## 结论先行

这一批改动解决了“用户愿意补充信息，但页面不知道如何承接”的一部分问题：有了选填问诊、确认页、撤回、来源展开、日常建议、今日感受和偏好保存，流程比上一版完整。

站在竞品或对家的角度，我不会先攻击功能数量，而会抓住四个更容易影响真实使用的缺口：

1. **安全判断仍依赖模型是否正确输出元数据**，自由输入急症时存在漏分流风险。
2. **主题识别把知识问题和个人症状混在一起**，八段锦知识问答会串出睡眠问诊和记录卡片。
3. **“有依据”目前是引用展示能力，不等于每个结论都被来源支持**；来源只覆盖睡眠，且引用依赖模型在正文中写标记。
4. **后续操作过多，用户完成回答后被四张卡片同时分流**，主任务反而不清楚。

因此，27 项测试通过可以证明工程回归做得扎实，不能证明意图命中率、急症召回率、引用准确率或用户满意度已经成立。

## 一、对家最容易抓住的 P0 问题

### P0-1：急症分流不是全链路的确定性能力

当前结构化问诊选择急症时，会在前端直接生成 120 提示；但自由输入主要依赖模型输出 `<<CARE>>` 元数据，界面只通过 `riskFor()` 的少量关键词兜底。模型如果漏写标记，或表达成“尽快就医”“可能需要立即处理”，页面仍可能继续展示普通调养、记录和偏好卡片。

代码证据：`public/app.js` 的 `run()` 只对结构化 `careData` 直接分流；`riskFor()` 只识别有限的文本表达和模型标记。

对家的质疑会是：**你们验收的是一个预先设计好的胸痛案例，不是急症识别能力。模型换一句话、少一个标记，页面会不会把用户带回日常调养？**

建议：

- 在请求模型前，对用户原始输入做本地高风险词和组合规则预筛，命中时先展示急救提示，再决定是否调用模型。
- 模型输出缺少结构化风险字段、字段解析失败或请求异常时，危险相关内容默认进入“谨慎就医”状态，隐藏普通调养卡片。
- 将急症召回率、误分流率和“危险场景是否出现普通建议”作为发布门槛，不能只测一条样例。

### P0-2：知识意图和症状意图串场

我在线上打开已有的“什么是八段锦”会话，回答本身是知识解释，但页面继续显示“补充睡眠情况”“睡眠日常建议”“记录今日感受”等卡片。原因是 `detectTopic()` 把“八段锦”直接映射为 `sleep`，而 `renderResultSteps()` 只看主题，不区分用户是在查知识还是描述自己的睡眠困扰。

这会带来两个问题：

- 用户只想知道八段锦是什么，却被推定为有睡眠问题。
- 用户会误以为八段锦和失眠之间存在产品已经确认的治疗关系。

建议：把 `intent` 和 `topic` 拆开。只有“个人症状/日常调养”意图才展示补充问诊和今日记录；“知识解释”只展示相关知识追问或“如果你是想解决自己的睡眠问题，可以开始梳理”这类明确的转入口。主题可以是睡眠，但不能因此自动假设用户有睡眠症状。

### P0-3：引用展示不等于引用正确

当前引用采用模型在正文中输出 `[来源:sleep-core]`，前端再把它转换成链接。模型没有输出标记时，页面显示“本轮未附可核验的引用”；输出标记时，页面默认认为对应资料支持这句话。实际线上八段锦知识会话就显示了“本轮未附可核验的引用”，但仍然呈现睡眠相关后续卡片。

对家的质疑会是：**你们究竟保证了“这句话被资料支持”，还是只保证了“这句话后面有一个链接”？**

建议：

- 让模型输出结构化的 `claims[]`，每条包含原文结论、来源 ID、来源支持范围和不确定性；不要让自由文本标记承担证据关系。
- 前端展示“这条资料支持什么”和“不支持什么”，避免用户把一篇睡眠科普误解为对个人情况的诊断依据。
- 为每个主题设置来源覆盖率；睡眠资料不能覆盖疲惫、消化、用药和女性周期。
- 来源卡片显示核对时间、适用范围和失效/更新策略。当前代码中的核对日期是固定文本，未来会产生新鲜度误解。

## 二、P1：用户完成流程后，体验仍可能变差

### P1-1：四张下一步卡片同时出现，主任务不清楚

普通回答完成后，页面可能同时给出补充情况、睡眠日常建议、记录今日感受、生成就医摘要四张卡片。再加上正文追问按钮和来源展开，用户要先做产品选择，才知道下一步。

对家可以把它描述为“把产品路线图直接塞给用户”。

建议按意图和风险排序：

1. 只保留一个主 CTA，例如“先补充一个关键情况”。
2. 一个次 CTA，例如“先看今天能做的一件事”。
3. 就医摘要放入更多操作或用户明确要带去就诊时再出现。
4. 记录今日感受只在用户已经完成一次建议或表达愿意持续记录时出现。

### P1-2：可以跳过，但不一定能顺利退出

问诊每一题都有“暂不填写”，但如果用户连续跳过，最终确认页的确认按钮会因为没有信息而不可用，页面没有一个同等明显的“返回对话/不保存”按钮。用户只能点右上角关闭，容易误以为流程卡住。

建议：在最终页提供明确的“暂不保存，回到对话”和“只保存我已填写的内容”两个动作；把“暂不填写”解释成“跳过这一项，不代表没有该症状”。

### P1-3：撤回被设计成修改流程里的隐含动作

功能上可以通过修改后暂不填写来撤回，但用户看到的是“修改”，不是“撤回这项信息”。健康记录一旦被确认，用户应该能看到当前事实、来源和撤回结果。

建议：确认页直接提供“修改”和“撤回”两个文案；撤回后显示时间线或状态：“已撤回，之后回答不会再使用”。

### P1-4：偏好保存的产品承诺比实际更大

“建议更合我意”容易被理解为助手会越来越懂我，但当前只保存“从作息/活动/饮食哪里开始”和饮食偏好文本。它们会进入后续模型请求，却没有按场景、时间和敏感度限定使用范围。

建议：改名为“日常偏好”，在保存按钮旁写清“仅用于日常建议，过敏信息会发送给模型服务”；提供本次不使用、只用于睡眠、有效期和一键清除全部记忆选项。不要把过敏或饮食限制和症状混在同一层记忆里。

### P1-5：同一会话的主题可能污染后续问题

当前会话会从前一轮回答和结构化事实推断下一轮主题。用户先问睡眠，再突然问“陈皮泡水适合谁”，后续卡片和来源可能仍沿用睡眠。长期对话里这会让用户觉得助手没有真正理解切换。

建议：每轮记录 `intent/topic/confidence`；当新问题与上一主题不一致时，显示轻量确认：“这次想聊陈皮，还是继续刚才的睡眠？”在切换前不要继续带入旧主题的建议卡片。

## 三、P1：可信度、隐私和可访问性

### P1-6：来源覆盖面太窄，产品却已经出现“建议依据”概念

目前精选资料集中在睡眠。用户在疲惫、消化、穴位和用药问题中看到“AI 一般信息”，会感受到不同主题的可信度不一致；如果团队下一步快速补很多来源，反而会出现来源质量不一的问题。

建议先选两个高频、高风险边界清晰的意图建立来源标准，再扩展主题。每个来源都做“可支持范围 / 不可支持范围 / 失效日期 / 人工复核人”字段。

### P1-7：本机历史、确认信息和偏好叠加后，隐私风险上升

当前保存的不只是聊天文本，还有睡眠时长、影响程度、否认的呼吸暂停、今日感受、饮食过敏和建议偏好。它们都在同一浏览器里可读，且页面只提示“同一浏览器其他使用者可能看到”。

建议：

- 首页首次出现睡眠记录或偏好时，给一次短而明确的本机存储提示。
- 增加“清除全部本机数据”，并显示会清除哪些内容。
- 导出文件默认脱敏文件名，明确包含确认信息、引用和偏好。
- 对过敏、妊娠、药物和严重症状增加敏感信息提示，不把它们作为普通偏好处理。

### P1-8：问诊选项的无障碍语义不准确

单选按钮使用 `aria-pressed` 后，在 Chrome 的辅助树里被读作 checkbox。用户每次点击后立即进入下一题，也没有一个明确的 radio group 和选中状态说明。

建议：使用 `role="radiogroup"` + `role="radio"` + `aria-checked`，或使用真正的 radio 控件；确认页和跳过按钮也要支持键盘顺序和焦点回收。

## 四、P2：可以暂缓，但需要记录为产品债务

- 图片/舌象识别仍未接入，后续必须先做图片质量和拒绝过度诊断，再做视觉模型。
- 实时搜索未接入，当前“精选资料”不应被包装为搜索结果。
- 女性周期仍是候选场景，先验证是否愿意记录实际状态，再做周期预测和关怀语气。
- 生态合作、企业微信、问诊承接和商业化没有接口、服务不可用兜底和结果归因定义。
- 当前没有线上埋点，27 项自动化测试不能替代真实用户行为数据。

## 五、建议下一批只做五件事

1. **确定性急症前置分流**：原始问题预筛、模型字段缺失兜底、普通卡片 fail-closed。
2. **意图与主题拆分**：知识问题不自动进入症状问诊，切换主题时让用户确认。
3. **证据关系结构化**：从“模型写引用标记”升级为“结论—来源—支持范围”的可校验结构。
4. **收敛后续 CTA**：一主一辅，减少四卡并列；摘要和今日记录按条件出现。
5. **隐私和可访问性**：清除全部本机数据、偏好用途提示、敏感信息提示、radio 语义和焦点管理。

## 评审判断

这批版本可以证明团队有较强的工程推进、回归测试和细节修复能力，但产品对外叙事不宜写成“已经解决了个性化问诊”。更准确的说法是：**完成了一个睡眠场景的结构化问诊和依据展示样板，下一步要验证它在不同意图、急症边界、引用准确性和真实用户行为下是否稳定。**
